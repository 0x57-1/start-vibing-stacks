# Advanced Datepicker

A calendar popover (or inline calendar) built on the third-party **vanilla-calendar-pro** library; `HSDatepicker` wraps it, merges a default style map with yours, swaps the month/year headers for `HSSelect` dropdowns, and formats the value back into the input.

## When to use
- Single date, multiple discrete dates, or a start→end range, with or without a time picker.
- Anything needing two months side by side (`"type": "multiple"`, `displayMonthsCount: 2`) or an always-open inline calendar (`inputMode: false`).
- **Do not use** for a month/quarter picker or a "last 7 days" preset row — a `select` or `dropdown` of named ranges is smaller and does not pull in vanilla-calendar-pro + lodash.
- **Do not use** for a plain birthdate field where a native `<input type="date">` is acceptable; this component styles nothing for free.
- Preline also ships a `datepicker` component (see `components/datepicker.md`) — that one is static markup. This one is the JS-driven library binding.

## Anatomy

Reduced skeleton (classes verbatim from `examples/third-party-plugins/advanced-datepicker/basic-usage.html`). Note the trigger is the **class** `hs-datepicker`, not the data attribute:

```html
<input
  class="hs-datepicker py-3 px-4 block w-full bg-layer border-layer-line rounded-lg sm:text-sm
         text-foreground placeholder:text-muted-foreground-1
         focus:border-primary-focus focus:ring-primary-focus
         disabled:opacity-50 disabled:pointer-events-none"
  type="text" placeholder="Select day"
  readonly                                          <!-- every example: the calendar owns the value -->
  data-hs-datepicker='{                             /* options only; NOT the init hook */
    "type": "default",                              /* "default" | "multiple" (+ displayMonthsCount) */
    "applyUtilityClasses": true,
    "dateMax": "2050-12-31",
    "mode": "custom-select",                        /* month+year become HSSelect dropdowns */
    "templates": {
      "arrowPrev": "<button data-vc-arrow=\"prev\">…svg…</button>",
      "arrowNext": "<button data-vc-arrow=\"next\">…svg…</button>"
    }
  }'>
```

The calendar panel itself is generated by the library — you influence it through `styles` (class strings, merged and **concatenated** onto the defaults) and `layouts` (template strings containing `<#CustomArrowPrev />`, `<#CustomArrowNext />`, `<#CustomMonth />`, `<#CustomYear />`, `<#Week />`, `<#Dates />`, `<#CustomTime />`, `<#Multiple>…<#/Multiple>` — every one of those appears in the example layouts).

**The calendar panel itself uses no moon tokens at all.** Grep `assets/js/preline/datepicker.js` for `bg-layer`, `bg-dropdown`, `text-foreground`, `bg-primary`, `muted-foreground` — every one returns **0 hits**. The built-in `templates` are hard-coded raw Tailwind with explicit `dark:` pairs — `bg-white` / `dark:bg-neutral-900`, `border-gray-200` / `dark:border-neutral-700`, `text-gray-800` / `dark:text-neutral-200`, `text-gray-500` / `dark:text-neutral-400`, and scrollbar classes down to `dark:[&::-webkit-scrollbar-thumb]:bg-neutral-500`. **That is the mechanism behind `selectedTheme: "light"`:** each template interpolates its `dark:` half as `${'light' !== theme ? 'dark:…' : ''}`, so `"light"` emits the class string *without* any `dark:` variants. So the tokens in the table above only ever reach the **input, nav buttons and modal chrome you write** — plus whatever you inject through `styles` / `layouts` (which is exactly why the examples put `text-foreground` on the layout's `/` separator and `bg-layer` in `styles.customSelect.shared`). Rebranding the panel means overriding `styles`, not switching theme.

The `custom-styles-for-selects` example deliberately uses **raw palette colours** for the per-field toggles (`text-red-600 dark:text-red-500`, `text-blue-600`, `text-green-600`, `text-yellow-600`, `text-purple-600`). Those are demo colours, not tokens — under moon they are the only hue on the whole calendar.

## Behaviour (JS)
Source: `assets/js/preline/datepicker.js` (`HSDatepicker`, v4.2.0), wrapping `VanillaCalendar` from vanilla-calendar-pro. Global: `window.HSDatepicker`. `autoInit()` runs on `window load`.

| Hook | Effect |
|---|---|
| `.hs-datepicker` **class** | The init selector: `autoInit()` queries `.hs-datepicker:not(.--prevent-on-load-init)`. |
| `data-hs-datepicker='{…}'` | JSON options, `JSON.parse`d and merged with any options passed to the constructor. Carries **no** init power on its own. |
| `--prevent-on-load-init` | Opts an element out of `autoInit()`. |

- **Defaults applied by the wrapper:** `selectedTheme: ''`, `dateMin: new Date().toISOString().split('T')[0]` (today), `dateMax: '2470-12-31'`, `mode: 'default'`, `inputMode: true`.
- **`applyUtilityClasses` is inert in 4.2.0.** It selects `templates` when truthy and `templatesBasedOnUtility` otherwise — and in this build those two modules are **byte-identical apart from the export name** (verified against `assets/js/preline/datepicker.js`). Setting it, omitting it, or setting it `false` all render the same panel. Every markup example passes `"applyUtilityClasses": true` except `modal-example.html`'s **second** picker, which omits it — and the two pickers still look the same. Keep passing `true` for forward-compatibility, but do not expect it to fix anything.
- **`mode: 'custom-select'`** replaces the month and year headers with `HSSelect` instances. `updateCustomSelects()` runs on `onShow` and `onCreateDateEls`; `destroySelects(context.mainElement)` runs on `onHide`. `onClickArrow` does **not** rebuild the selects — it defers (`setTimeout`) `disableNav()` + `disableOptions()` + `updateCalendar()`, which is what greys out months/years past `dateMin`/`dateMax`.
- **`styles` are merged with `_.mergeWith` and string values are CONCATENATED**, not replaced: `styles: {calendar: 'z-80'}` appends `z-80` to the default calendar classes. Pass `removeDefaultStyles: true` to start from `{}`.
- **Your lifecycle callbacks run first, then Preline's.** The wrapper composes `onInit`, `onShow`, `onHide`, `onUpdate`, `onCreateDateEls`, `onChangeToInput`, `onChangeTime`, `onClickYear`, `onClickMonth`, `onClickArrow` as `yours(); ours();`.
- **Change notification, two ways**, both fired from `onChangeToInput` with the same payload `{selectedDates, selectedTime, rest}` (`rest` = the vanilla-calendar context):
  - `instance.on('change', (payload) => …)` — registers a callback on the wrapper (`HSBasePlugin.on`), one handler per event name.
  - a `CustomEvent('change.hs.datepicker')` dispatched on `this.el` with `bubbles: true, cancelable: true` — read it as **`evt.detail.payload`**, not `evt.detail`.
- **Value formatting:** `dateFormat` is matched longest-first by a hand-rolled scanner (`formatDate`), and this is the exhaustive token set — `YYYY`, `dddd`, `MMMM`, `ddd`, `MMM`, `YY`, `MM`, `DD`, `HH`, `mm`, `ss`, then single `Y`, `M`, `D`, `H`, `m`, `s` (unpadded). Anything else is copied through literally. The field separator is inferred from the **first non-alphanumeric character** of `dateFormat` (`extractSeparatorFromFormat`), else `inputModeOptions.dateSeparator`, else `.`. Multiple values join on `inputModeOptions.itemsSeparator` (default `", "`).
- **`replaceTodayWithText: true`** prints a localized "Today" (`dateLocale` → built-in table covering `pt-BR`→"Hoje", `es`, `fr`, `de`, `it`, `ru`, `pl`, `uk`, `zh-CN`, `ja-JP`, …).
- **Escape hatches:** `instance.vanillaCalendar` (the raw library object, with `.context.selectedDates`, `.context.inputElement`, `.context.mainElement`) and `instance.getCurrentState()`.
- **Statics:** `HSDatepicker.autoInit()`, `HSDatepicker.getInstance(elOrSelector, true)` → `{id, element}`.
- **`destroy()`** tears down the calendar, drops the collection entry, and — if the original input was removed from the DOM — **re-creates a clone** with the same attributes, classes and value at the same position.

## Gotchas
- **The class initialises it, the attribute does not.** `autoInit()` matches `.hs-datepicker`. An element with `data-hs-datepicker` but no `hs-datepicker` class is inert, with no error; the reverse (class, no attribute) initialises with pure defaults.
- **`readonly` is on every input example on purpose.** Remove it and the user can type a string the calendar never parses; the wrapper only ever writes *into* the field.
- **`dateMin` defaults to today.** Omit it and past dates are unreachable — which silently breaks any "date of birth" or historical-range field. All 14 markup examples set `dateMax` but none set `dateMin`.
- **`styles` append, so you cannot remove a default class by naming it.** `z-80` works because it is additive; to *replace* the panel styling you need `removeDefaultStyles: true`.
- **Inside a modal you must raise the panel.** Both pickers in `modal-example.html` add `"styles": {"calendar": "z-80"}` to match the dialog's own `z-80`; without it the calendar renders behind the overlay.
- **`selectedDates` ranges are one string, not two.** `["2030-01-01 2030-01-17"]` is a range; `["2030-01-01", "2030-01-17"]` is two discrete dates. `selectionDatesMode` decides which the input formatter prints.
- **The inline example keeps input-only utility classes.** `placeholder:` and `focus:ring-*` on a `<div>` are dead weight; harmless, but do not copy them as evidence that a div can be focused.
- **`light-theme.html` drops the token system entirely** (`border-gray-200`, `focus:border-primary`). `selectedTheme: "light"` pins only the *panel*; the input still follows the page unless you hard-code it as that example does.
- **Re-init after dynamic render:** `autoInit()` skips elements already in `window.$hsDatepickerCollection`, and unlike other Preline plugins it does **not** prune detached nodes. Call `instance.destroy()` before unmounting or the stale entry blocks a later re-init on a rebuilt element with the same id.
- **`destroy()` may hand you a different DOM node.** When the input was removed it inserts a clone and repoints `this.el`; any reference you held to the original is stale.
- **Init timing is `load` + `requestAnimationFrame`** in `destroy-reinitialize-datepicker.js` and `with-navigation-controls.js`. `getInstance` inside a bare `load` handler can race the wrapper's own `load` listener and return `null`.
- A11y: the trigger is a `readonly` text input with no `aria-haspopup` / `aria-expanded` in any example, and the arrow templates are bare `<button>`s with icon-only content and no `aria-label`. Add names yourself.
